# 手工重构后的 C++ 架构重建与 recon 契约目录验证

日期：2026-08-11

## 目的

用户手工调整了源码布局与 recon 契约实现。此前维护性审计的文件路径、文件数和下一候选
已经不能作为当前工作区事实，因此本轮从构建配置、实际源码和测试入口重新建立基线。

## 当前架构

- `native/src` 的活跃实现按 20 个领域目录组织，不再有根目录活跃 `.cpp/.hpp`。
- `server/main.cpp` 是纯 C++ CLI 组合根；149 项命令由 `registry/` 的 11 个领域 appender
  保持公开顺序，HTTP features/OpenAPI 复用同一命令表。
- `server/` 负责 HTTP 监听、请求解析、路由和响应；领域查询仍在各自模块内，不回流到组合根。
- `formula/` 分为源码分析、Parser/AST、环境构建、宿主上下文、函数调度、运行时、Render IR、
  扫描和回测；普通公开非 L2 注册边界已经收口，剩余仅为未来函数策略、授权 L2 序列、
  券商私有信号、交易状态或插件回调边界。
- `cloud/` 承载 TQLEX、PBRPC、TPool 与云计算协议；`data/` 承载 JSN、证券目录、板块和披露；
  `research/corporate/funds/institution/...` 使用目录、归一化、抓取缓存、服务和命令适配分层。
- `recon/` 负责 224 项 API 契约与诊断，不依赖正式 8765 服务即可在进程内验证响应。

## 最新 recon 手工重构

16 个契约文件已经从顶层 `contract_id` 长条件链改为：

1. 独立 `validate_*` 校验函数；
2. `constexpr std::array` 的 id→函数目录；
3. `static_assert(unique_contract_ids())` 的编译期重复检查；
4. 小型循环分发器。

合计 81 个校验函数、115 个契约目录项和 16 个编译期唯一性检查。文件中仍出现的两处
`else if (contract_id == ...)` 位于共享校验函数内部，用于同一处理器下的细分语义，不是
残留的顶层分发链。

增量构建首先发现 `recon_contract_market_data_quote.cpp` 的
`validate_stock_native_valuation()` 已变为 `void`，却保留了原分发器的 `return true;`。
将其改为提前 `return;` 后，受影响目标恢复编译。

## 后续规则

当前已不存在 5,000 行以上的生产单体，不能继续把“行数较大”本身当作拆分理由。下一步应从
真实功能缺口、缺陷或明确职责混合中选择；`jsn`、公式函数、TPool、PBRPC 等共享模块只有在
实际需要修改时再按语义域拆分并使用定向宽回归。公式解释器普通公开非 L2 注册项已收口，
后续解释器推进必须由新 DLL 证据、合法输入或真实失败公式驱动，不能按函数名猜测实现。
