# TDataParse 本地盘口快照结构

> 结论日期：2026-08-07。证据来自 `TDataParse.dll!fn_TGetImageData`、
> `TdxW.exe` 调用链、缓存解压路径和原 DLL/纯 C++ 实现的逐字节差分测试。

## 结论

`fn_TGetImageData` 不是图片解码器，也不是实时 TCP 收包入口。它把一段由
控制字符分隔的增量字段流，恢复为有状态的 **1032 字节盘口快照数组**。
快照包含 OHLC、最新价、累计量额、十档买卖价量、买一/卖一委托队列和若干
尚未完成业务命名的辅助字段。

主程序中的来源路径为：

```text
T0002/zst_cache/<市场前缀><代码>_<日期>.<扩展名>
  └─ 24 字节包装头
      └─ zlib 数据（流起点 +24）
          └─ 控制字符字段流
              └─ fn_TGetImageData
                  └─ 1032 字节快照数组
```

历史下载路径使用 `hishf/date/<日期>/<前缀><代码>.<扩展名>`，当日路径使用
`todayhf/<前缀><代码>.img`。当前安装的 `zst_cache` 为空，所以结构验证采用
可重复的合成字段流，并由原 DLL 作为参考实现。

## 缓存包装

文件头至少为 24 字节；已确认的字段如下：

| 偏移 | 类型 | 含义 |
|---:|---|---|
| `+8` | `uint32` | zlib 压缩数据长度 |
| `+16` | `uint32` | 解压后长度 |
| `+24` | bytes | zlib 流起点 |

`TdxW.exe` 的解压函数可确认使用 zlib 1.2.13。未标定的头字段必须原样保留，
不能按文件名或零值猜测含义。

## 控制流语法

每个字段由两字节 ASCII 标签和文本值组成：

```text
0x03 <tag0> <tag1> <value...> 0x02   普通字段结束
0x03 <tag0> <tag1> <value...> 0x04   字段结束并提交一条快照
```

- `0x03` 清空当前字段缓冲；
- `0x02` 应用字段但不提交记录；
- `0x04` 应用字段并提交当前完整状态；
- 单个字段在原实现中最多占用 100 字节缓冲；
- 状态跨记录继承，因此后续记录只需要携带变化字段；
- 时间相同，或上一条时间为零时，新状态覆盖上一条；
- 合并后再删除除时间字段外完全相同的相邻快照；
- 去重完成后，`+64` 由相邻累计成交量之差计算。

## 1032 字节布局

所有整数均为小端；`double` 为 IEEE-754 64 位浮点数。

| 偏移 | 大小 | 线标签 | 当前语义 |
|---:|---:|---|---|
| `0` | 4 | `0T` | `HHMMSS` 时间整数 |
| `4` | 8 | `04` | 昨收 |
| `12` | 8 | `05` | 开盘 |
| `20` | 8 | `06` | 最高 |
| `28` | 8 | `07` | 最低 |
| `36` | 8 | `08` | 最新价 |
| `44` | 8 | `1C` | 保留浮点字段；当前 TdxW 消费方均不读取 |
| `52` | 8 | `1D` | 保留浮点字段；当前 TdxW 消费方均不读取 |
| `60` | 4 | `09` | 主程序按持仓量读取 |
| `64` | 8 | 派生 | 本条累计量减上一条累计量 |
| `72` | 8 | `10` | 累计成交量 |
| `80` | 8 | `1A` | 累计成交额 |
| `88` | 80 | `20..29` | 买一至买十价格，10 个 `double` |
| `168` | 80 | `30..39` | 买一至买十数量，10 个 `uint64` |
| `248` | 80 | `40..49` | 卖一至卖十价格，10 个 `double` |
| `328` | 80 | `50..59` | 卖一至卖十数量，10 个 `uint64`；线值先按浮点解析再转换 |
| `408` | 8 | `1E` | 保留浮点字段；当前 TdxW 消费方均不读取 |
| `416` | 8 | `1F` | 保留浮点字段；当前 TdxW 消费方均不读取 |
| `424` | 8 | `1G` | 买均：平均买价，`double` |
| `432` | 8 | `1I` | 卖均：平均卖价，`double` |
| `440` | 8 | `1H` | 总买：买方总量，`uint64` |
| `448` | 8 | `1J` | 总卖：卖方总量，`uint64` |
| `456` | 4 | `62` | 买一委托队列报告数量 |
| `460` | 4 | `62` | 卖一委托队列报告数量 |
| `464` | 200 | `64` | 买一委托队列，最多 50 个 `uint32` |
| `664` | 200 | `64` | 卖一委托队列，最多 50 个 `uint32` |
| `864` | 168 | `0D` | NUL 结尾文本，最多保留 167 字节；返回后当前 TdxW 消费方均不读取 |

委托队列使用一组状态标签：`60` 选择买侧、`61` 选择卖侧并重置写入游标；
其值小于等于零时同时清空对应数量和数组。`62` 写报告数量，`63` 清空当前
数组，`64` 依次追加数量，最多写入 50 项。

## 原 DLL 差分验证

32 位参考宿主 `output/tdataparse_reference_check.cpp` 构造三条增量记录，
分别覆盖 OHLC、十档首档、两侧委托队列、状态继承和相邻重复去除；它把同一
份输入交给原版 `ida/TDataParse.dll`。随后：

```powershell
build\native-mingw\tdx-tool.exe image-data decode `
  --input output\tdataparse-synthetic-control.bin `
  --input-format raw --limit 0 `
  --record-output output\tdataparse-native-records.bin
```

原 DLL 与纯 C++ 实现均输出 2 条记录、2064 字节，SHA-256 相同且逐字节
差异数为 0。生成物仅是合成测试数据，不含账号、票据或真实行情。

`1G..1J` 的业务名另由主程序消费方静态闭合：`TdxW.exe:0xA26C90` 将四项
映射到分钟 UI 结构，`0xA207C0` 分别使用界面标签“买均/总买/卖均/总卖”。
这组名称来自消费方标签和字段映射，不依赖猜测值域。进一步枚举
`fn_TGetImageData` 已解析函数指针的全部直接交叉引用后，确认
`0x59DA50/0x5B4DD0/0xA19E10/0xA26C90/0xA637E0/0xA85600` 六个实际
消费入口均不读取 `+44/+52/+408/+416`；`0x7218F0` 只是
`GetProcAddress` 加载入口，不计作消费方。因此 `1C..1F` 在当前 TdxW 构建中
定性为“线协议保留、主程序未消费”，继续保留线标签，不猜测业务名称。
同一审计还确认六个入口均不访问 `+864..+1031` 的 `0D` 返回区。`0D` 并非
完全无作用：解析器提交记录前仍会继承它，并把它纳入相邻快照相等性判断；这里只
能定性为“返回后未被当前主程序消费”。

差分测试还暴露了原 DLL 的一个容量边界：它用
`source_length / 1032` 估算初始输出容量；若这个估算小于实际提交记录数，
扩容分支只复制 `record_count - 1` 条，可能留下一个全零洞。真实缓存通常不会
触发该条件；纯 C++ 解码器使用动态容器，不复刻这个丢记录缺陷。

## 统一工具

```powershell
tdx-tool image-data decode --input <缓存文件> --input-format auto
```

命令完全离线，不加载原 DLL：

- `auto` 自动识别 24 字节 zlib 包装，否则按原始控制流处理；
- JSON 使用稳定 schema `tdx-image-data-snapshots-v3`，四项已命名字段位于
  `aggregate_order_book`，全部直接消费方审计位于 `consumer_audit`；
- `--record-output` 可额外写出标准化 1032 字节记录；
- 未识别线标签保留在 `unknown_fields`，避免新版本字段静默丢失；
- `1C..1F/0D` 保留在线标签键下；当前版本的六个直接消费方均不读取它们，未来
  只有出现新构建消费代码或可交叉验证的业务样本时才升级名称。
